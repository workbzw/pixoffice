## 浏览器检查

本轮通过本地 Vite 页面检查：
- 当前办公室正常绘制。
- 多人演示包含走动、侧身听说与回座位。
- 打开人物预览后关闭，主场景仍继续显示和执行。
- 1440 x 900 和 390 x 844 视口均可显示办公室。
- 开发热更新后再打开/关闭预览，复现了旧缓存回收新画面仍使用的纹理。已让热更新保留同一份资源租约缓存并补回归；修正后重复该流程并持续运行演示，未观察到新的 JavaScript error。不将此描述为已穷尽所有 GPU 故障。

这不是对全部屏幕和全部故障路径的穷举验证，也不是帧率/显存基准测试。原素材已有的自然程度和接触细节不因结构整理而变为已修复。

## 以后增加场景的验收

1. 用独立场景 ID，明确初始世界、占地、角色及物品状态。
2. core 可无 DOM/Pixi 运行，不导入素材加载器。
3. 人工编辑和协议编辑通过同一校验，不绕开碰撞。
4. 无固定工位的角色、短交互、多人同时执行、等待、取消和恢复都有测试。
5. 行业行为在场景插件中定义，不把课堂或工厂判断写进通用运行时。
6. 需要新原语时明确升级接口，而不是让某个场景偷偷改通用含义。

教室保持当前机位，黑板在画面后方，学生背向镜头；教师和学生的独立动作需新素材。原地起立但继续占用座位需要单独设计，不能用现有离席动作冒充。

## 以后增加动画适配器的验收

1. 资源元信息可先读取；能力、视向、组合和接触规格真实。
2. 四向移动使用宿主距离时钟，不能改变逻辑路径。
3. 各实例独立，共用贴图时互不销毁。
4. 取消或关闭期间的晚到资源不挂载回已销毁的场景。
5. 坐起、工作、讲话、姓名、物品遮挡和点击区域与既有约定一致。
6. 一个真实骨骼人物与帧人物混合运行，再开展性能和批量资源制作。
7. Cue/动作完成不绕过运行时成为业务成功事件。

## 后续性能验证

需要固定设备、视口、DPR、网络、资源版本，记录多次样本。当前只完成正确性回归，未声称达到性能目标。

建议分别测量：
- 6 人办公室的首屏、互动准备、帧耗时和显存。
- 20 人共用/独立外观，区分实例成本和纹理成本。
- 帧与真实骨骼混合。
- 连续打开关闭预览、切换场景后的资源稳定平台。

保留 `pixoffice:background-visible`、`pixoffice:scene-ready`、`pixoffice:actions-ready` 标记。帧率、内存及20人规模必须实测后再承诺。

## 分工边界

- 内核维护者：协议、状态、导航、占用与取消。
- 场景开发者：core 插件、布局、家具及场景表现映射。
- 动画开发者：适配器、资源生命周期、采样与挂点。
- 素材制作人员：人物图片或骨架、动作、注册点、能力与版本。
- 应用集成人员：注册场景与适配器，连接页面和外部服务。

先维护仓库内的真实模块边界；多个实现通过共同验收后，再拆成可发布 npm 包。接口存在、参考实现完成和真实骨骼迁移成功是三个不同的状态。
