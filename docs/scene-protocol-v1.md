# AI Office 独立场景协议与对象模型

状态：设计草案，尚未实现。协议目标版本：1.0。

注意：本文件是历史草案。当前实现已升级到 2.0 整数格协议，空间模型以 [整数格与家具互动](./integer-grid-and-interactions.md) 为准，不再采用本文的连续坐标设想。

本文用于约定新场景内核与外部项目的边界，不描述当前已有能力，也不替代当前 README 中的旧 HTTP 接口。现有运行时、画面和动画不因本文发生改变。

## 1. 产品边界

AI Office 是独立、可被协议驱动的二维互动场景客户端，不绑定任何 Agent、工作流或业务领域。

- 外部项目负责业务任务、AI 推理、任务调度、真实进度、交付文件和业务数据。
- 前端负责场景对象、空间布局、寻路、互动、动画、界面和用户操作反馈。
- 协议负责传递有明确含义的指令、展示状态、能力描述、执行事件和场景快照。
- 场景动作完成不是业务任务完成。业务任务完成也不要求等待人物返回工位。
- 前端不执行外部传入的 JavaScript、Shell、Skill 或业务工作流。

第一版保留现有人物和办公室视觉。新内核不是室内设计软件、游戏编辑器或 Agent 平台。

## 2. 模块边界

```text
外部业务项目
    |
    | 版本化协议
    v
Transport Adapter -> 协议校验 / 权限检查 -> OfficeRuntime
                                              |
                        +---------------------+--------------------+
                        |                     |                    |
                    World Model        Space / Interaction     Command Ledger
                        |                     |                    |
                        +---------------------+--------------------+
                                              |
                                       只读状态 / 事件
                                              |
                                      Pixi View / React UI

Editor -> Layout Draft -> 校验 -> OfficeRuntime
Persistence Adapter <-> 布局 / 检查点 / 命令记录 / 事件发件箱
```

依赖约束：

1. 协议定义不依赖 React、Pixi、Electron 或具体网络库。
2. 场景内核为纯 TypeScript，不引用 DOM、Pixi 实体、网络客户端或 UI Store。
3. Runtime 是每个场景实例的唯一状态写入入口；状态可在内部原地更新，不要求每帧深拷贝整个世界。
4. 渲染器读取场景状态，维护自己的插值、贴图和动画播放状态，不向内核回写人物坐标。
5. 本地菜单、编辑器和外部命令遵守同一套校验和资源占用规则。
6. 不使用全局场景单例。每个场景拥有独立的 Runtime、队列、时钟和存储命名空间。
7. 不把每帧位置广播给 React 或网络；UI 订阅相关状态变化，渲染器读取高频运动状态。

建议实现模块为 `protocol`、`core`、`view`、`editor`、`adapters`。先采用项目内模块，不提前建设多仓库、微服务或完整 ECS 框架。

## 3. 世界与对象模型

### 3.1 基础对象

| 对象 | 内容 | 不包含 |
| --- | --- | --- |
| Scene | 场景 ID、坐标规则、模板引用、对象集合、布局版本 | AI 会话、业务数据库 |
| Template | 资源引用、默认占地、锚点、能力、视觉映射 | 某个具体员工的当前任务 |
| Actor | 稳定 ID、模板、位置、业务展示状态、场景行为状态、绑定关系 | 模型密钥、Agent 实现 |
| Prop | 稳定 ID、模板、位置、各能力的状态 | 任意可执行脚本 |
| Group | 成员 ID 和相对变换，用于组合移动，例如桌子与椅子 | 独立的任务调度系统 |
| Binding | 人物与座位等对象的逻辑关系 | Pixi 父子节点关系 |

显示名称可以更改；`entityId` 不随名称、数组排序或素材替换改变。人物序号仅用于旧接口转换，不进入新内核。

工位是组合对象，不是所有物品必须继承的基类。人物绑定椅子的 `seat` 锚点，但不成为椅子或工位的子对象，因此离座后可以自由行走。

组合成员只能有一个布局父对象，组合关系不能成环。删除被引用的对象必须拒绝，或在显式事务中同时解除关联，不能悄悄将人物绑定到其他椅子。

### 3.2 空间模型

- 世界坐标为逻辑坐标，原点在左上，X 向右，Y 向下，和显示像素、屏幕缩放无关。
- 场景声明世界尺寸、网格尺寸和网格原点，不把当前 960 x 640 尺寸写死在协议中。
- 编辑器将物品吸附到网格，人物在世界坐标中连续运动。
- 占地、视觉边界、交互锚点分开定义；不能用大头人物的贴图宽度作为通行半径。
- 模板锚点使用对象局部坐标，运行时结合布局计算世界坐标。外部通常引用对象和锚点，不发送逐帧坐标。
- 第一版只支持平移、无缩放的物品摆放；保留变换结构不等于已支持旋转编辑。
- 导航图、世界锚点和预订信息是派生数据，不作为需要外部维护的第二套布局。

### 3.3 业务展示状态与行为状态分离

一个人物可以同时处于：

```text
业务展示：正在分析竞品资料，关联 task-42
场景行为：正在走向白板，关联 cmd-101
视觉表现：背向行走第 2 帧
```

外部通过专门命令更新业务展示；运行时决定运动和互动状态；渲染器决定动画帧。三者不能共用一个含义混杂的 `state` 字段。

`working` 等业务展示值只代表外部声明的状态，不证明后台真的在工作。第一版不自动创造业务进度或交付结果。

### 3.4 模板与能力

能力是前端可信 TypeScript 模块，不是 Agent Skill。模板组合能力，实例保存能力对应的状态。

| 对象示例 | 能力示例 | 状态示例 |
| --- | --- | --- |
| 人物 | 移动、说话、参与对话 | 当前行为、展示标签 |
| 椅子 | 入座、独占使用 | 占用者，由运行时维护 |
| 白板 | 内容显示 | 标题、文本，由授权命令更新 |
| 电脑 | 电源、内容显示 | 开关、受控内容引用 |
| 饮水机 | 取水、独占使用、资源消耗 | 剩余水量、使用者 |
| 跑步机 | 电源、持续使用、独占使用 | 运行状态、速度 |

每种能力声明版本、输入和状态 Schema、可写字段、前置条件、资源需求、超时、取消和清理方法。新增普通物品只添加模板；新增行为机制可以增加能力模块，不要求全部用 JSON 实现。

能力状态中区分外部可写字段与运行时只读字段。例如白板内容可写，但不能通过状态补丁伪造椅子占用者或人物坐标。

资源清单只引用经前端认可的素材和模板。缺少可选视觉资源时可降级；缺少必要行为能力时拒绝相关操作，不能将其报告为成功。

## 4. 协议契约

### 4.1 通用约定

- 传输格式为 JSON；规范来源计划使用版本化 JSON Schema，TypeScript 类型与其保持同步。
- 消息携带 `protocolVersion`、`sceneId`；命令必须具有 `commandId`。
- 身份由传输层认证，不信任消息自己声明的发送者身份。
- 去重键为认证主体、`sceneId`、`commandId`。相同 ID、不同内容返回 `COMMAND_ID_CONFLICT`。
- 外部使用实体 ID 和语义操作，不引用 Pixi 对象、内部函数名、素材帧编号。
- 命令的 `params` 由对应操作 Schema 严格校验，不是可以绕过校验的任意对象。
- 主版本不兼容时拒绝握手。新增可选字段可以使用次版本，但新操作和能力仍需协商。
- 错误码面向程序，说明文字面向用户；中文说明不能代替稳定错误码。

### 4.2 能力发现与查询

建立连接后，外部可获得：

- 支持的协议版本、操作及参数 Schema。
- 场景对象的 ID、名称、类型、能力和可引用锚点。
- 当前布局版本、场景检查点版本，以及可用于对齐事件流的位置。
- 文本长度、队列数量、消息大小等限制。
- 对具体命令的状态查询能力。

客户端必须区分“能力存在”和“当前可用”。椅子支持入座，但此刻可能被占用。

### 4.3 第一版命令集合

| 命令 | 含义 | 约束 |
| --- | --- | --- |
| `actor.presentation.set` | 更新人物任务标题、业务状态和关联信息 | 携带该人物展示通道的递增 `sourceRevision`，拒绝旧版本覆盖 |
| `actor.moveTo` | 走向指定对象的可达锚点 | 运行时规划路线，不接收逐帧坐标 |
| `actor.say` | 展示文字气泡，持续有限时间 | 不声称完成了真实业务对话 |
| `actor.interact` | 执行对象公布的交互，如对话、入座、取水 | 包含接近、预约、互动和资源释放 |
| `object.state.set` | 更新某一能力允许外部修改的状态 | 补丁原子校验；不允许修改位置、预约等内核字段 |
| `command.cancel` | 取消指定命令 | 权限检查，返回明确的取消结果 |
| `layout.apply` | 提交完整布局草稿 | 编辑权限、布局版本检查、空间和引用完整性校验 |

布局提交需要 `expectedLayoutRevision`。能力状态的并发修改使用该能力的 `expectedStateRevision`，不使用每帧位置变化导致的全局版本冲突。

任务展示通道第一版只有一个业务写入主体。本地场景菜单不修改真实业务展示；多业务来源需先在外部完成汇总，不能用多个来源各自的计数器互相覆盖。

组合流程由外部依次发送命令或等待结果。第一版不增加任意脚本、复杂条件分支或前端工作流 DSL。

### 4.4 命令示例

```json
{
  "protocolVersion": "1.0",
  "sceneId": "office-1",
  "commandId": "cmd-101",
  "type": "actor.interact",
  "actorId": "wang-ming",
  "targetId": "chen-shu",
  "interaction": "talk",
  "params": {
    "text": "请分析这份竞品资料。",
    "durationMs": 3000
  },
  "busyPolicy": "queue",
  "expiresAt": "2026-09-26T08:10:00Z",
  "timeoutMs": 30000,
  "correlationId": "task-42"
}
```

`busyPolicy` 第一版只允许 `queue` 或 `reject`，默认 `queue`。不做隐式抢占；需要中断时先取消旧命令，再提交新命令。

`expiresAt` 限制最晚开始时间，排队时也检查；`timeoutMs` 从执行开始计时，限制整个接近和互动过程。握手提供宿主时间以估计时钟偏差，执行时长使用单调时钟。没有指定时采用公布的有限默认值。

`correlationId` 只是关联外部任务，不赋予场景结束业务任务的权限。

## 5. 执行、失败与并发

### 5.1 生命周期

```text
收到消息 -> 校验失败 -> rejected
         -> 校验通过 -> queued -> running -> completed
                          |         +----> failed / cancelled
                          +--------------> expired / cancelled / failed
```

- `queued` 表示已接受并记录，不是已开始或已完成。
- 出队时重新检查对象、权限、布局、前置条件和有效期；不能只在接收时检查一次。
- 超过执行时间返回 `failed`，错误码 `EXECUTION_TIMEOUT`。
- `completed`、`rejected`、`failed`、`cancelled`、`expired` 是终态；终态不可被迟到回调重新改成成功。
- `command.cancel` 有自己的命令 ID，目标通过 `targetCommandId` 指定；已结束的目标返回其现有结果，不伪造取消成功。
- 取消停止后续执行并清理资源，不默认撤销已经展示的文字、已消耗的水量等效果。

事件示例：

```json
{
  "protocolVersion": "1.0",
  "sceneId": "office-1",
  "runtimeId": "runtime-a",
  "eventId": "event-204",
  "eventSeq": 204,
  "type": "command.status",
  "commandId": "cmd-101",
  "status": "failed",
  "error": {
    "code": "NO_ROUTE",
    "message": "无法到达目标人物的对话位置。",
    "retryable": false
  }
}
```

`eventSeq` 在同一 `runtimeId` 内递增。重启使用新 `runtimeId`，不能将不同实例的序号直接比较；`eventId` 用于事件重传去重。

基础错误码包括 `INVALID_COMMAND`、`UNSUPPORTED_VERSION`、`UNSUPPORTED_CAPABILITY`、`ENTITY_NOT_FOUND`、`BUSY`、`QUEUE_FULL`、`NO_ROUTE`、`PRECONDITION_FAILED`、`REVISION_CONFLICT`、`FORBIDDEN`、`EXECUTION_TIMEOUT`、`RUNTIME_RESTARTED`、`OUTCOME_UNKNOWN`。

### 5.2 并发与资源

- 同一人物一次只有一个占用身体的动作。不同人物在资源不冲突时可并行。
- 更新业务展示不占用人物身体，不因人物正在行走而阻塞，也不强迫人物立刻回座。
- 对话需要同时取得双方的交互许可；使用物品需要取得对应交互槽位。
- 多资源预约由运行时一次性检查和分配；拿不到全部资源时不持有部分资源等待，避免互相占用。
- 排队项不提前占据物品；资源释放必须覆盖成功、失败、取消、超时和场景销毁。
- 队列有容量和等待期限，不无限积压。明确公布顺序策略：同一人物的身体动作按接收顺序执行，互不冲突的人物可并行推进。
- 第一版布局提交仅允许在场景移动和交互均空闲、且没有待执行空间命令时发生，否则返回 `BUSY`；不隐式清空队列或暂停外部业务任务。

### 5.3 幂等与恢复边界

命令 ID 不等于天然实现“恰好执行一次”。可靠实现需要命令记录、检查点和待发送事件的持久化支持。

- 网络允许重复投递。已知命令返回已有状态，不重复启动。
- 适配器接收批次后，先持久化收件记录，再确认接收；事件进入持久化发件箱后重试发送，直到外部确认。
- 已接受命令使用本地单调顺序号保持顺序，不能依赖网络响应到达顺序。
- 普通网络断开时，在执行租约仍有效的范围内，已接受的有限动作可继续完成，结果暂存；不继续获得新业务指令。租约到期时停止执行并清理预约，不无限离线运行。
- 页面刷新或崩溃不等于普通断线。先恢复布局和检查点，再与外部对账，不自动重放曾经开始的动作。
- 能确认尚在执行且已中断的命令报告 `RUNTIME_RESTARTED`；无法确认其结果时报告 `OUTCOME_UNKNOWN`，由外部查询或决定是否重新下达。
- 对保留记录范围外的旧命令不能假定“从未执行”。协议公布记录保留边界，过期重复请求要求外部对账。
- 恢复采用布局、稳定展示状态和已提交能力状态，不恢复动画帧、纹理或过期预约；人物先放到经过验证的安全位置，再接受新动作。
- 场景检查点携带布局版本和对应事件位置；重连先读取检查点，再补后续事件，不能乱序覆盖。

首版同一场景只允许一个执行实例。HTTP 宿主需通过执行租约与世代号拒绝第二个实例同时消费命令及写入结果；失去租约的客户端停止执行。多窗口只读镜像和无缝接管不属于首版。

## 6. HTTP 适配方案

协议不要求前端开服务端。独立网页主动连接外部项目提供的接口；现有本地网关以后可以作为开发适配器，但不能成为场景内核依赖。

建议接口草案：

| 接口 | 作用 |
| --- | --- |
| `POST /scene-api/v1/scenes/{sceneId}/sessions` | 版本和能力协商，认证后创建执行租约，返回服务端时间、检查点和消费起点 |
| `POST /scene-api/v1/scenes/{sceneId}/sessions/{sessionId}/renew` | 续租；过期实例不得继续提交状态 |
| `GET /scene-api/v1/scenes/{sceneId}/commands?cursor=...` | 按不透明游标拉取或长轮询命令，读取本身不删除命令 |
| `POST /scene-api/v1/scenes/{sceneId}/receipts` | 持久化收件后确认批次和游标；接收确认不是执行结果 |
| `POST /scene-api/v1/scenes/{sceneId}/events` | 批量上报执行事件和用户事件，宿主按事件 ID 去重并确认 |
| `PUT /scene-api/v1/scenes/{sceneId}/checkpoint` | 保存与事件位置对应的场景检查点，检查租约和检查点版本 |
| `GET /scene-api/v1/scenes/{sceneId}/commands/{commandId}` | 按认证主体查询命令记录与已上报结果，用于对账 |

命令游标与事件序号是两条不同的数据流，不能混用。租约身份通过请求头携带，宿主验证权限和世代号；过期写入必须拒绝。

外部项目先把业务请求转换为协议命令并写入自己的命令来源。AI Office 不规定外部业务系统如何接受用户任务。

只有一个在途拉取请求，带超时、指数退避和抖动；网络恢复后根据已持久化游标补取。队列、消息体和事件批次都设上限。限流和暂停不能无限增加内存占用。

原有 `/actions` 接口在迁移期继续由兼容适配器处理，但其能力不能被描述为具备新协议的可靠性保证。若接口没有客户端命令 ID，就不能跨刷新可靠去重。

以后需要 `postMessage` 或 Electron IPC 时，只增加适配器，不改对象模型和语义命令。嵌入模式必须检查消息来源与 origin；不能使用无条件接收的通配消息通道。

## 7. 本地编辑与安全

- 编辑器只改布局草稿，应用时检查边界、占地、锚点可达性、引用完整性和版本冲突。
- 版本不匹配时保留用户草稿并报告冲突，不直接覆盖外部的新布局。
- 布局提交成功后，统一重建受影响空间数据并发出 `layout.changed`，本地保存和远端检查点均基于已提交版本。
- 用户点击人物、物品或文件时发出白名单事件，由业务适配层决定是否请求业务动作；点击不等于允许任意代码执行。
- 区分观察、展示控制、人物控制、布局编辑等权限，按场景授权。
- 浏览器不携带大模型密钥；场景连接凭据应可撤销、限域，不写入公开的 Vite 构建变量或源码。
- 外部文本按纯文本或经过安全处理的 Markdown 展示，不解释为原始 HTML。
- 文件和媒体使用受控内容引用；外部 URL、协议和资源大小需校验，不允许通过内容引用访问任意本地路径或加载可执行代码。
- 没有必要的素材时使用占位；能力故障在清理资源后结束当前命令，不自动让整场景停止。进程崩溃等不可隔离故障按恢复协议处理。

## 8. 实施顺序与验收

### 阶段 A：冻结最小合约

交付协议 Schema、TypeScript 类型、能力描述、合法和非法消息样例、兼容版本测试。HTTP 接口路径与持久化细节仍需在实现前通过最小联调验证，不能只凭本文宣称已支持。

### 阶段 B：不依赖画面的内核

实现两个角色、两张椅子和一台饮水机。使用可控制的时钟测试移动、交互、占用和取消，测试无需启动 Pixi 或浏览器。

### 阶段 C：接回现有视觉

复用当前人物、办公室、帧动画和坐下姿态。逻辑依赖语义姿态，渲染器自行映射素材；不同动画技术只替换渲染适配，不修改协议。

### 阶段 D：连接与编辑

接入 HTTP 测试宿主、命令记录和恢复流程，再增加布局草稿编辑。旧 HTTP 命令通过边缘适配转换，不在新内核继续保留固定人物序号等历史约束。

最低验收项：

- 不认识业务和 AI 的独立前端，可以被一个普通 HTTP 测试项目驱动。
- 重复命令不重复执行，相同 ID 不同内容被拒绝。
- 队列溢出、人物忙碌、无路可走、目标丢失均有明确结果。
- 取消、超时、删除和销毁后没有遗留预约。
- 人物移动时更新业务展示，不丢失路线，也不伪造业务完成。
- 两个人争用一个物品时可以顺序使用，不互相永久等待。
- 断网重连、页面刷新、事件重传和执行租约过期均可解释、可恢复或明确报告不确定结果。
- 旧布局提交不能覆盖新布局，恢复快照不会恢复过期预约。
- 资源缺失可降级，未知能力被拒绝，不因无效命令导致白屏。
- 两个独立场景实例的数据、队列和销毁流程互不影响。
- 桌面与移动端均能完整呈现场景，连续执行时不产生无界队列或每帧 React 重渲染。

## 9. 第一版明确不做

不做任意插件代码加载、浏览器内业务执行器、多端共同编辑、场景多人联网同步、自动业务决策、任意家具旋转缩放和完整游戏引擎。

扩展原则：普通新物品改模板，新机制加能力，新传输加适配器，新视觉换渲染器。不能保证任何需求都零修改，但应让每类修改有清晰且可测试的归属。
